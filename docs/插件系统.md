# 插件系统（一切皆插件）

## 一句话

LionBox 里能开关的东西**都是插件**：60 个工具、4 个技能、终端限制、Agent 大循环、
子智能体、智能体团队、自动授权审查、自动化任务 —— 一共 9 类。
每一类都能在设置里单独开关，关掉之后它提供的能力**从下发给模型的清单里消失**（不是只改个显示），
外部 jar 还能热插拔（放进去 → reload → 生效；卸掉 → 立刻消失）。

## 插件分 9 类

| kind | 中文名 | 是什么 | 现在有哪些 |
| --- | --- | --- | --- |
| `BASE_TOOL` | 基础工具 | 极简模式就能用的工具 | 文件读写/检索、`execute_command` 等 |
| `ADVANCED_TOOL` | 进阶工具 | 只有标准模式开放的工具 | 网络、Git、编解码等 |
| `SKILL` | 技能 | 往系统提示词注入领域经验 | `core/plugin/skill/` 下的 4 个技能 |
| `SUBAGENT` | 子智能体 | 派子任务给"另一个自己"，可限层级/并发/模型 | `plugin.subagent` |
| `TERMINAL` | 终端 | 常驻终端的行为约束（跑多久、吐多少） | `plugin.terminal` |
| `AGENT_LOOP` | Agent 大循环 | 主循环策略（轮次上限、工具超时、空转容忍） | `plugin.agent-loop` |
| `AGENT_TEAM` | 智能体团队 | 用户自定义的一组智能体（模式 + 职责） | `plugin.agent-team` |
| `APPROVAL_REVIEW` | 自动授权审查 | 让另一个模型审核危险调用 | `plugin.approval-review`（**默认关**） |
| `AUTOMATION` | 自动化任务 | 按时间/周期在指定会话里自动干活 | `plugin.automation` |

**基础工具 / 进阶工具是自动判定的**：判据就是工具自己那句
`isAvailableInMode(AgentMode.MINIMAL)` —— 极简模式能用 = 基础工具，否则 = 进阶工具。
所以新增一个工具插件**不需要**声明自己属于哪一类，也不会出现"两处规则各写一份、日后走偏"。

## 文件都在哪

| 路径 | 是什么 |
| --- | --- |
| `<用户主目录>/.lioncode/plugins/` | **插件目录**（`GET /api/plugins` 返回的 `pluginsDir`），外部 jar 放这里 |
| `<用户主目录>/.lioncode/plugins/settings.json` | 用户开关 + 各类插件参数（重启后还在，就靠它） |
| `<用户主目录>/.lioncode/plugins/dev/<插件id>/` | 插件开发模式生成的工程 |
| `<用户主目录>/.lioncode/plugins/sdk/lionbox-plugin-api.jar` | 编译插件用的接口包（开发模式自动导出） |

`<用户主目录>/.lioncode/` 就是 `app-config.json` 所在的那个目录，跟现有 `AppConfigStore` 一套约定。

> **为什么不用 `application.yml` 里的 `lion.plugin.scan-path` 当主目录**：
> pom 对 `src/main/resources` 开了 Maven 资源过滤，`${user.home}` 在**打包时**就被替换成
> 构建机的家目录写进 jar 里了（实测 jar 内写着 `default-path: C:\Users\Leo/lion-code-workspace`）。
> 拿它当插件目录，换台机器就指到一个不存在的地方。所以主目录一律按**运行时** `user.home` 现算；
> 老的 `scan-path` 没有丢，它仍然会作为**额外扫描目录**（存在才扫），老用户放在那儿的 jar 照样能加载。

## 设置里的开关是怎么"真的生效"的

开关存下来只是第一步，真正生效靠 `PluginGateSpi`（实现 `AgentSpi`，挂在 Agent 主循环上）：

1. 用户在设置里点掉 `read_file`（插件 id `tool.file.read`）；
2. 下一轮构建提示词时，`AgentSpi.filterToolNames` 把 `read_file` 从工具清单里摘掉；
3. 模型根本看不到这个工具 —— 它不会去试，也就不会出现"调一次 ❌、换个写法再 ❌"的烧轮次现象。

关掉 ≠ 卸载：插件仍在注册表里（列表上还能看到、随时能打开），只是不再下发给模型。
真要让它从进程里消失，用 `DELETE /api/plugins/{id}`（卸载）。

几个特殊关系：

- **终端插件**管着一组工具（`execute_command` / `run_background` / `stop_background`）。
  关掉终端插件 = 这三个工具一起消失（见 `TerminalPlugin.OWNED_TOOL_NAMES`）。
- **自动授权审查默认关闭**：它会在每次危险调用前多打一次模型对话，对本地模型是实打实的几十秒，
  这种"明显改变体感"的能力必须用户主动开。
- **技能（SKILL）的开关**：开关状态、列表、持久化都已就绪，但"关掉后不再注入提示词片段"
  目前还差一步接线 —— 注入方是 `SkillCatalogSpi`（技能系统那边），它需要读一次
  `PluginSettings.isEnabled(技能插件)` 再决定跳不跳过。详见文末"已知坑"。

## 热插拔（外部 jar）

| 动作 | 怎么做 | 发生了什么 |
| --- | --- | --- |
| 装 | 把 jar 放进插件目录 | 每个 jar 用**独立 ClassLoader** 加载，与主程序隔离 |
| 生效 | `POST /api/plugins/reload`（或重启） | 先卸掉全部外置插件，再从头扫一遍 |
| 卸 | `DELETE /api/plugins/{id}` | 从注册表 + 事件总线 + `AgentSpi` 里摘干净，`close()` 掉 ClassLoader，它贡献的工具同时消失 |

加载器认三种"我是插件"的声明方式（取并集）：

1. `META-INF/lionbox-plugin.properties` 里的 `plugin.class=包名.类名`（推荐）；
2. `META-INF/services/com.lioncode.core.plugin.Plugin`（ServiceLoader 约定）；
3. 都没有就扫 jar 里所有 class（兼容老插件包，最慢但能认）。

**坏 jar 不会让应用起不来**：目录不存在、目录是空的、jar 是半成品、类加载抛异常，
全部只记一条错误，并且**以 `jar:xxx.jar` 的形式出现在插件列表里**（带 `error` 字段、`broken: true`）。
这是"我明明放了 jar 怎么列表里什么都没有"的唯一解药 —— 出问题要看得见。

## 终端插件：两个限制

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| `maxCommandSeconds` | `300` | 一条命令最长跑多少秒。超时由 `PersistentShell` 连终端一起杀掉重建（老行为就是这样） |
| `maxOutputBytes` | `200000` | 一条命令最多带回多少字节。超出截断，并**明确告诉模型"输出已截断"**（0 = 不限制，即老行为） |

- 模型自己写的 `timeout` 只是"期望"，用户设的上限是"规定"，**取小值**（`TerminalPlugin.clampTimeout`）。
- 截断在**读取侧**做：一条 `type huge.log` 能产出几十兆，先全读进内存再切会白吃一遍内存。

改的入口：`POST /api/plugins/settings/terminal {"maxCommandSeconds":60,"maxOutputBytes":50000}`。

## Agent 大循环插件：三个参数

| 设置 | 默认值 | 原来的行为 |
| --- | --- | --- |
| `maxIterations` | `200` | AgentLoop 里的兜底轮次上限 |
| `toolTimeoutSeconds` | `600` | `lionbox.agent.tool-timeout-seconds` 的默认值 |
| `silentRounds` | `2` | 连续"模型什么都没吐"的容忍轮数（`MAX_CALL_REPAIR`） |

它实现 `AgentSpi.loopOptions`，AgentLoop 通过 `AgentSpi.loopInt(sessionId, key, 默认值)` 读。
插件关掉 = 返回空表 = 主循环回到自己的默认值，这就是开关该有的语义。
默认值刻意与"现在实际行为"对齐，所以**不装插件也不会改变任何现有行为**。

## 四类"会干活"的插件：本轮做到哪一步

| 插件 | 已经有了 | 留给 AgentLoop 主循环接线的部分 |
| --- | --- | --- |
| 子智能体 | 配置（递归层级/并发/模型）、持久化、开关、**层级强制校验** `checkSpawn(depth)` / `checkConcurrency(running)` | 真正的派发：拿到 `null` 才放行，非 null 时把返回的字符串**当作工具结果**回给模型 |
| 智能体团队 | 成员增删改查（名字/模式/职责/模型/是否启用）、持久化、把团队说明注入系统提示词 | 把任务派给某个成员（需要一个派发工具） |
| 自动授权审查 | 配置（用哪个提供商/模型、审哪些工具）、判定骨架 `check(...)`、给审查模型的提示词 `buildReviewPrompt(...)`、结论解析 `parseVerdict(...)`、拦截话术 `denyMessage(...)` | 在 `runToolWithTimeout` 之前调 `check`，`needsReview=true` 时发一次对话拿 `ALLOW/DENY`，DENY 就**当工具结果回给模型**（不要抛异常打断整条任务） |
| 自动化任务 | 任务增删改查（时间/周期/会话/指令）、纯函数 `pollDue(now)`、`markRun(id, when)` | 谁来驱动：在会话驱动循环里定时调 `pollDue`，把到点任务的 prompt 推进那条会话的串行队列；**跑完一定要调 `markRun`**，否则会重复触发 |

四者都**不起自己的线程**：AgentLoop 是按会话串行推进的，插件自己起线程会让"这个会话现在有几件事在跑"
没人说得清（谁的上下文、谁的审批、谁的工作区）。

## settings.json 长什么样

```json
{
  "enabled": { "tool.file.read": false, "plugin.approval-review": true },
  "terminal":  { "maxCommandSeconds": 300, "maxOutputBytes": 200000 },
  "loop":      { "maxIterations": 200, "toolTimeoutSeconds": 600, "silentRounds": 2 },
  "subagent":  { "maxDepth": 1, "maxConcurrency": 3, "provider": "", "model": "" },
  "review":    { "enabled": false, "provider": "", "model": "", "tools": ["execute_command"] },
  "team":      { "members": [] },
  "automation":{ "tasks": [] },
  "devMode":   false
}
```

两条规则：

1. **只存和默认值不一样的开关**：没动过的插件不在文件里出现，这样以后改代码里的默认值能自然生效，
   不会被一份陈年老配置按在原地。
2. **原子落盘**：先写 `settings.json.tmp` 再 move 覆盖。用户点开关那一刻正好强杀进程，
   也不会留下半截 JSON（那会导致"下次启动所有设置丢了"）。

## 已知坑（不在本次改动范围内，已上报）

1. **`application.yml` 里的 `${user.home}` 在打包时就被替换掉了**（pom 对 `src/main/resources`
   开了 `filtering=true`）。打出来的 jar 里写着 `default-path: C:\Users\Leo/lion-code-workspace`，
   于是 `lion.workspace.default-path`、`lion.event.store-path`、`lion.plugin.scan-path`
   在别人机器上全部指向构建机的路径。插件目录已经按运行时 `user.home` 兜住了，其余两处建议一并修
   （要么关掉对 `application.yml` 的过滤，要么改用 Spring 的 `${user.home}` 转义写法 `#{systemProperties['user.home']}`）。
2. **原生工具通道没有走插件过滤**：文本通道下提示词里的工具清单走的是 `filteredTools(...)`（会按开关摘除），
   但 `buildToolDefinitions(mode)` 直接用了 `pluginRegistry.getToolsByMode(mode)`。
   也就是说 `toolCallMode=native` 时，关掉的插件，它的**函数定义仍会下发给模型**，
   而且真被调用时还能执行（执行路径只按名字找工具）。建议 `buildToolDefinitions` 也过一遍 `AgentSpi` 过滤。
3. **提示词末尾那张"别选错工具"对照表是静态文案**，里面点名了 `read_file` / `execute_command` 等。
   插件关掉后清单里没有它们了，但对照表还在提 —— 模型可能因此去调一个不存在的工具（会被拒绝）。
   建议该表按当前可用工具动态生成。
4. **技能插件的开关还没接到提示词注入上**：`SkillCatalogSpi`（`core/plugin/skill/`，技能系统负责）
   在拼技能目录与正文时没有查 `PluginSettings`。加一行"这个技能的插件被关了就跳过"即可，
   开关数据本身已经在 `settings.json` 里了。

```powershell
python tools/checks/_check_plugin_system.py
```

覆盖：9 类齐全、工具自动分类、关掉的插件工具从清单消失（对照前后数量）、开关重启后仍在、
