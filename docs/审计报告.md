### A-1【高·待修】会话持久化把 URL 上的 sessionId 直接当文件名 → 任意 `.json` 文件删除/写入

- **文件**：`src/main/java/com/lioncode/core/session/SessionPersistence.java:62,75,118`、`src/main/java/com/lioncode/core/session/ConversationHistory.java:118,131,152`、触发点 `src/main/java/com/lioncode/web/controller/SessionController.java:132-137`
- **现象**：`DELETE /api/sessions/{sessionId}` 会把 `{sessionId}` 原样拼进文件名：

```java
// SessionPersistence.java:116-119
public void deleteSession(String sessionId) {
    Path filePath = sessionsDir.resolve(sessionId + ".json");
    Files.deleteIfExists(filePath);
```

- **为什么是 bug**：`Path.resolve()` 不校验、不规范化。`sessionId = "..\..\..\Users\Leo\Desktop\important"` 时，实际路径变成
  `<workspace>/.lioncode/sessions/..\..\..\Users\Leo\Desktop\important.json`，
  Windows 自己展开 `..` → **删掉工作区之外任意一个 `.json` 文件**（加 `.json` 后缀是唯一限制）。写同理（`saveSession` 用的是内部 UUID，风险小；删/读是直接可达的）。
- **触发条件**：`DELETE /api/sessions/..%5C..%5C..%5CUsers%5CLeo%5CDesktop%5Cfoo`（`%5C` 是段内合法编码，Spring MVC 默认不拦；不带编码的 `\` 在 URL 里也常被接受）。`destroyAllSessions` 只会用内部 ID，不受影响。
- **建议改法**：
  1. 加白名单校验（会话 ID 是本服务自己生成的 UUID）：`if (!sessionId.matches("[A-Za-z0-9-]{8,64}")) return;`
  2. 再加一道 `Path p = dir.resolve(id + ".json").normalize(); if (!p.startsWith(dir)) return;`
  3. 我在 `EventStore` 里加的 `safePathSegment(String)`（`core/event/EventStore.java:160`）可以直接复用同一套思路，但**跨包引用需要提升可见性或复制一份**，建议放到一个公共工具类里（如 `core/workspace/PathSafety`）。
- **复现等级**：代码路径推理（未实机验证：不想对用户正在跑的实例做删除型测试）。建议 Lead 转给 Session 负责人时用"新建一个测试会话 + 改名成穿越串再删"这种无害方式验证。

### A-2【高·已修】工作区沙箱可被"相对路径 + `..`"绕过（写/读/删全都逃得出去）

- **文件**：`src/main/java/com/lioncode/core/workspace/WorkspaceContext.java:63-84`（改前）
- **现象**：沙箱只校验**绝对路径**，相对路径直接拼接返回：

```java
// 改前
if (p.isAbsolute()) {
    ... if (!abs.startsWith(wsPath)) throw new IllegalStateException("路径在工作区之外...");
    return rawPath;
}
if (ws == null || ws.isBlank()) return rawPath;
return Path.of(ws).resolve(p).toString();     // ← 不规范化、不校验
```

- **为什么是 bug**：`Path.resolve()` 不做规范化。`path=..\..\escaped.txt` 会得到 `C:\ws\inner\proj\..\..\escaped.txt`，工具调用 `Files.writeString` 时由操作系统展开 `..`，文件落在工作区外两层。**所有文件类工具都经过 `AbstractToolPlugin.resolvePath()` → `WorkspaceContext.resolve()`**（grep 到 33 处调用，覆盖 write/read/delete/modify/copy/move/glob/search/tree/wc/info/chmod/touch/mkdir + git + download），所以这是一个模型（或被提示词注入的用户内容）可直接触发的沙箱逃逸，属于"越权"类里的最高优先级。
- **触发条件**：模型发出 `write_file(path="..\\..\\任意文件")`，或 `path="sub/../../../evil"`。
- **已修**（`WorkspaceContext.resolve`）：
  - 相对路径也 `normalize()` 后校验仍在工作区内；
  - 绝对路径额外做 `toRealPath()` 校验（符号链接/junction 不再能绕过，父目录不存在时用父目录判断）；
  - 校验顺序改成"先归一化再判断"（改前是判断未归一化的串）；
  - `strict=false` 的行为保持不变。
- **证据（旧行为实测）**：用一个最小 Java 探针复刻改前逻辑：

```
workspace  = ...\wsdemo\inner\proj
old resolve= ...\wsdemo\inner\proj\..\..\escaped.txt
outside file created = true          ← 文件真的落在工作区外
```

- **回归套件**：`tools/checks/_check_audit_workspace_sandbox.py`（A1~A5，直接对 `target/classes` 断言，9/9 通过）

### A-4【高·已修】原生文件夹选择对话框会把 HTTP 线程永久挂死，并让"选择目录"功能彻底不可用

- **文件**：`src/main/java/com/lioncode/web/controller/NativeDialogController.java:255-272`（改前）
- **现象**：先**阻塞读完 stdout**，再 `waitFor(300, SECONDS)`：

```java
// 改前
Process process = pb.start();
try (BufferedReader reader = new BufferedReader(new InputStreamReader(process.getInputStream(), ...))) {
    String line;
    while ((line = reader.readLine()) != null) { stdout.append(line).append('\n'); }   // ← 阻塞到子进程退出
}
boolean finished = process.waitFor(300, TimeUnit.SECONDS);                              // ← 形同虚设
```

- **为什么是 bug**：PowerShell 进程要等用户关掉选择窗口才退出（`-WindowStyle Hidden` 只隐藏控制台，对话框是模态的）。用户把窗口晾着不点：`readLine()` 永不返回 → **HTTP 线程永久占用**（Tomcat 线程耗尽后整个服务无响应）；`finally` 里的 `DIALOG_OPEN.set(false)` 也永不执行 → 之后所有请求都被"文件夹选择窗口已打开"拒绝，**只能重启应用**。
- **触发条件**：点"选择工作区"后不选也不取消（离开座位）。
- **已修**：把 stdout 重定向到临时文件（`pb.redirectOutput(stdoutFile)`），**先 `waitFor(300s)` 再读文件**；超时则 `destroyForcibly()` + 等 5 秒 + 继续读诊断输出，返回明确提示"对话框等待超时（5 分钟），已关闭"。

### A-5【高·已修】本地模型启动等待循环读 `this.process` 字段 → 用户点"卸载"时抛 NPE

- **文件**：`src/main/java/com/lioncode/model/runtime/LocalModelRuntime.java:1213-1234`（改前 `spawn`）
- **现象**：

```java
// 改前
process = pb.start();                       // 字段赋值
while (System.currentTimeMillis() < deadline) {
    if (!process.isAlive()) { ... process.exitValue() ... }   // ← 每次都读字段
```
  而 `killProcess()`（`stop()`/重启/预热打断→`/api/runtime/local/stop`）会执行 `process = null;`。

- **为什么是 bug**：典型的"字段被并发置空"竞态。用户在模型加载中（phase=starting，最长 300 秒）点"卸载模型"，等待循环下一轮 `process.isAlive()` → **NullPointerException**，从 `ensureRunning()` 冒到适配器 → 用户看到"模型调用失败: null"，而不是"启动被中止"。
- **触发条件**：`POST /api/runtime/local/start` 之后立刻 `POST /api/runtime/local/stop`。
- **已修**：改用局部变量 `Process started`，循环里判 `process != started`（说明这次启动已被 stop/另一次 spawn 取代）→ 返回"启动被中止"并记日志；`started.isAlive()/exitValue()` 一律走局部变量。

- **文件**：`src/main/java/com/lioncode/model/runtime/LocalModelRuntime.java:824-842`（改前 `downloadTarget`）、调用链 `downloadModelIfAllowed()`（`:588`）→ `downloadFileIfAllowed(effectiveModelFile())`（`:636`）

```java
// 改前
private Path downloadTarget(String file) {
    String name = (file == null || file.isBlank()) ? effectiveModelFile() : file;
    for (Path dir : appDirs()) { ... return dir.resolve(name); }    // ← name 可含 ..\..\
```

### A-7【高·已修】事件列表用"并发 Map + 普通 ArrayList"组合 → 事件丢失/异常，轮询线程可能踩到并发修改

- **文件**：`src/main/java/com/lioncode/core/event/EventStore.java:47,77,107`（改前）
- **现象**：

```java
private final Map<String, List<LionEvent>> sessionEvents = new ConcurrentHashMap<>();
...
sessionEvents.computeIfAbsent(event.sessionId(), k -> new ArrayList<>()).add(event);   // ← 值是普通 ArrayList
...
public List<LionEvent> getSessionEvents(String sessionId) {
    return List.copyOf(sessionEvents.getOrDefault(sessionId, List.of()));               // ← 一边复制一边被追加
```

- **为什么是 bug**：`ConcurrentHashMap` 只保护了**键**，值是不安全的 `ArrayList`。
  1. 同一个会话的写入线程（会话 worker / 虚拟线程在 `AgentLoop` 里 `recordEvent`）并发 `add` → 丢更新、`ArrayIndexOutOfBoundsException`、`size` 与实际不符；
  2. HTTP 轮询线程（`GET /api/events/{id}?after=`，前端 800ms 一次）`List.copyOf` 正在被追加的列表 → `ConcurrentModificationException` / 数组越界 → 500；
  3. 多会话并发（`AgentLoop` 的工具线程 + 事件记录）时最明显。
- **触发条件**：并发写同一会话的事件（多工具并行、或"事件轮询 + 工具执行"同时发生）——前端每 800ms 轮询一次，属于常态。
- **已修**：值改成 `CopyOnWriteArrayList`（写少读多，迭代天然安全），`getSessionEvents` 增加 null/空白 sessionId 的短路返回。

### B-1【中·已修】`Files.walk` 不关闭 + `retention-days` 是死配置 → 启动时把全部历史事件读进内存

- **文件**：`src/main/java/com/lioncode/core/event/EventStore.java:211-240`（改前 `loadEventsFromDisk`）
- **现象/证据**：

```java
var paths = Files.walk(eventStorePath).filter(p -> p.toString().endsWith(".json")).toList();  // ← 流没关
```
  且 `@Value("${lion.event.retention-days:30}") private int retentionDays;` **全项目没有任何地方读它**（javadoc 却写着"自动清理过期事件"）。
- **为什么是 bug**：① `Files.walk` 持有打开的目录句柄，Windows 上会一直占着事件目录；② 每次启动把**所有**历史事件（每条一个 JSON 文件）全量加载进 `sessionEvents`+`eventIndex`，长期使用内存只增不减（`clearSession` 没有任何调用方）。
- **已修**：`try (var stream = Files.walk(...))`；按 `retention-days` 跳过过期日期目录（**磁盘文件不动**，只控制内存层）；新增 `lion.event.max-events-per-session`（默认 2000）给每个会话的内存事件数封顶，超出从最老的丢并同步清理 `eventIndex`。前端只按 `?after=` 拉增量，不需要回看几千条历史，所以上限不影响 UI。

### B-2【中·已修】`ask_user` 被"停止"取消后，模型收到的是"用户没回答，请继续"

- **文件**：`src/main/java/com/lioncode/core/question/UserQuestionService.java:89-106`（改前）
- **现象**：

```java
while (System.currentTimeMillis() < deadline) {
    if (w.latch.await(POLL_MS, TimeUnit.MILLISECONDS)) {
        break;                       // ← 取消也是 countDown，于是从这里出去
    }
    if (w.cancelled) { return CANCELLED; }   // ← 永远走不到
}
if (w.answer != null && !w.answer.isBlank()) { ... }
return TIMEOUT;                      // ← 被取消的提问走到这里
```

- **为什么是 bug**：`cancelSession()`（`POST /api/chat/control/stop` 触发）先置 `cancelled=true` 再 `countDown()`，`await` 立刻返回 true → `break` 跳过循环内的取消判断 → 落到 TIMEOUT 分支，回给模型的是"（用户 300 秒内没有回答。请不要再重复提问，先基于现有信息给出你能做的部分…）"。用户明明按了停止，模型却被鼓励继续干活。
- **触发条件**：模型调用 `ask_user` 等待期间，用户点停止。
- **已修**：循环之后、答案判断之前补 `if (w.cancelled) return cancelled(...)`，取消文案改为明确的"请不要继续执行，等用户下一步指示"。另外给 `answer()` / `cancelSession()` 补了 null 参数短路（`ConcurrentHashMap.get(null)` 会抛 NPE）。

### B-3【中·已修】`usage` 字段缺失或为 `null` 时抛 NPE，把一次成功的回答整段丢掉

- **文件**：`src/main/java/com/lioncode/model/adapter/OpenAICompatibleAdapter.java:536-543`（改前）、`AnthropicAdapter.java:327-334`（改前）
- **现象**：

```java
if (root.has("usage")) {
    JsonNode usageNode = root.get("usage");
    usage = new ModelResponse.TokenUsage(
        usageNode.get("prompt_tokens").asInt(), ...);   // usage:null 或只有 total_tokens → NPE
```

### B-5【中·已修】`GET /api/models` 复用 900 秒读超时的客户端 → 端点半死时占满 Tomcat 线程

- **文件**：`src/main/java/com/lioncode/model/adapter/OpenAICompatibleAdapter.java:348`（改前）
- **为什么是 bug**：`httpClient` 的 `readTimeout` 是 15 分钟（同步聊天需要），但 `/models` 是"拉清单"，端点在"端口通但不回包"状态下会让每个设置页请求挂 15 分钟。

### B-6【中·已修】流式请求不响应"取消" → 用户点停止后 SSE 仍然跑到底

- **文件**：`src/main/java/com/lioncode/model/adapter/OpenAICompatibleAdapter.java:288-292`、`AnthropicAdapter.java:116-118`（改前）
- **为什么是 bug**：`Flux.create(sink -> ...)` 没有注册 `sink.onCancel/onDispose`，下层 OkHttp `EventSource` 收不到取消信号。本地模型 11 token/s、一轮可能几分钟，用户点停止（或前端断开）后连接与算力照旧被占着。
- **已修**：用 `EventSource[] holder` 保存当前连接，`sink.onCancel/onDispose` → `cancelQuietly(holder[0])`（`EventSource.cancel()`；已结束的连接上是空操作）；降级重试分支也把 holder 传下去。

### B-7【中·已修】适配器配置：`(String)` 强转可能抛 CCE，字段非 volatile 导致"改了配置不生效"

- **文件**：`src/main/java/com/lioncode/model/adapter/OpenAICompatibleAdapter.java:91-101`、`AnthropicAdapter.java:71-79`（改前）
- **为什么是 bug**：① `(String) config.get("baseUrl")` 对 `{"baseUrl":123}` 抛 `ClassCastException`，且是在"保存配置"的请求里炸；② `baseUrl`/`apiKey` 是普通字段，HTTP 线程写、worker 线程读，JMM 下没有可见性保证（`toolsRejected` 是 volatile，说明作者知道这件事，但漏了这两个）。
- **已修**：`safeStr()` 宽松取值（null→保留旧值，其它类型 `String.valueOf`）+ 字段 `volatile`。

### B-8【中·已修】`app-config.json` 截断式写入 → 崩溃/磁盘满一次就静默丢光用户全部配置

- **文件**：`src/main/java/com/lioncode/model/config/AppConfigStore.java:552-563`（改前 `saveToDisk`）
- **为什么是 bug**：`Files.writeString(configFile, json)` 是"先截断再写"。写到一半断电/杀进程/磁盘满 → 文件是半截 JSON → 下次启动 `mapper.readValue` 抛异常被 `catch (IOException)` 吞掉（只留一行 error 日志）→ 用户填的端点、密钥、模型、llama 参数**全部丢失**。
- **已修**：写同目录 `app-config.json.tmp` → `Files.move(..., ATOMIC_MOVE)`，不支持原子移动的文件系统退回普通替换。

### B-9【中·已修】模型启动失败时读全量日志 → 失败路径上再吃一次 OOM

- **文件**：`src/main/java/com/lioncode/model/runtime/LocalModelRuntime.java:1330`（改前 `tailLog`）
- **为什么是 bug**：`Files.readAllLines(lionbox-model.log)` 把整个日志读进内存。llama-server 每个请求都写日志，跑一天几百 MB；而 `tailLog()` 恰好只在"启动失败"时调用（`ensureRunning` 里），属于雪上加霜。
- **已修**：改用 `RandomAccessFile` 只读尾部 64KB，掐掉半行后取最后 15 行。

### B-10【中·已修】设置页改端口后本地模型"永远启动失败"（探活端口与启动端口不一致）

- **文件**：`src/main/java/com/lioncode/model/runtime/LocalModelRuntime.java:1238-1243`（改前 `healthy`）、`:1314-1320`（`portFree`）
- **现象**：`spawn()` 用 `cfgInt("port", port)`（设置页可改）拉起进程，`healthy()` 却一直探字段 `port`（application.yml 默认 8788）。
- **为什么是 bug**：改端口=8789 后，进程在 8789 正常服务，健康检查永远连 8788 → 白等满 `start-timeout-seconds`（默认 300s）后报"等待 N 秒仍未就绪"，然后回退 CPU 再等 180s。用户看到的是"模型起不来"，实际早好了。
- **已修**：新增 `effectiveHost()/effectivePort()`（配置优先），`healthy()`/`portFree()` 统一使用。
- **提示**：`baseUrl()` 仍返回字段端口（对外契约不变，避免影响前端与 `manages()` 的判断）——如果 Lead 希望"改端口后端点也跟着变"，那是一次有意的行为变更，需要单独确认。

### B-11【中·已修】`taskkill` 输出管道无人读取 + 超时后进程对象泄漏

- **文件**：`src/main/java/com/lioncode/model/runtime/LocalModelRuntime.java:1301-1311`（改前 `taskkillTree`）
- **为什么是 bug**：`redirectErrorStream(true).start()` 默认把 stdout 接成管道而没人读，输出超过管道缓冲区（约 64KB）就永久阻塞；`waitFor(15s)` 超时后既不 `destroyForcibly` 也不关流，`Process` 对象与句柄一起泄漏。
- **已修**：`redirectOutput(Redirect.DISCARD)` + 超时 `destroyForcibly()` + `finally` 兜底强杀 + PID ≤0 直接返回。

### B-12【中·已修】开机预热线程不是守护线程 → 关窗后 JVM 迟迟不退出

- **文件**：`src/main/java/com/lioncode/model/runtime/PrewarmService.java:111`（改前）
- **为什么是 bug**：`warmUp` 会阻塞到模型加载完（`ensureRunning` 最长 300s）+ 一次模型请求（读超时 900s）。非守护线程会让 JVM 一直活着，用户看到"点了关闭进程还在"。
- **已修**：`setDaemon(true)`。

### B-13【中·已修】`lion.queue.capacity` 配置从未生效，队列无上限 → 可被无限入队打到 OOM

- **文件**：`src/main/java/com/lioncode/queue/MessageQueue.java:38-46`（改前）
- **为什么是 bug**：`application.yml` 写着 `lion.queue.capacity: 1000`，但**没有任何代码读它**；`PriorityBlockingQueue` 的 64 只是初始容量，队列实际无上限。循环 `POST /api/chat` 就能把消息无限堆在堆里（每条还带一个 `CompletableFuture`）。
- **已修**：接上配置（`@Value("${lion.queue.capacity:1000}")`）；达到上限时**普通消息**返回一个已完成异常的 future（`ChatController` 会把它变成 `success=false` 的可读错误），**Steer 插队消息不受限**（它就是用来救场的）。这是"配置本来就承诺的行为"，不是新增语义。

### B-14【中·已修】`POST /api/workspaces/permission` 空参数 → NPE → 500

- **文件**：`src/main/java/com/lioncode/web/controller/WorkspaceController.java:72-85`（改前）

### B-15【中·已修】`POST /api/workspaces` 空路径 → NPE 500；`path=""` → 把进程 CWD 静默注册成工作区

- **文件**：`src/main/java/com/lioncode/web/controller/WorkspaceController.java:26-30` + `src/main/java/com/lioncode/core/workspace/WorkspaceManager.java:37-44`（改前）

### B-16【中·已修】前端每次启动都会把用户设的工作区权限重置回"工作区写"

- **文件**：`src/main/java/com/lioncode/core/workspace/WorkspaceManager.java:30-32`（改前 `registerWorkspace(String)`）
- **为什么是 bug**：`GET /api/workspaces/default`（前端初始化必调）→ `registerWorkspace(desktop)` → `workspaces.put(id, new Workspace(id, path, WORKSPACE_WRITE))` **无条件覆盖**。用户手动设成 READ_ONLY / FULL_ACCESS 后，下次启动就被改回 WORKSPACE_WRITE —— 这是权限语义上的静默降级/升级。

### B-17【中·已修】`POST /api/approvals` 系列空参数 → NPE → 500

- **文件**：`src/main/java/com/lioncode/web/controller/ApprovalController.java:51-84`（改前）

### B-18【中·已修】下发模型时把"用户级配置 Map"当请求体，任意键都会写进配置文件

- **文件**：`src/main/java/com/lioncode/web/controller/RuntimeController.java:238-246` + `src/main/java/com/lioncode/model/config/AppConfigStore.java:470-484`（部分修）

## 四、打包与配置（不在我写权限内，需 Lead 转交）

### D-1【高·待修】Maven 资源过滤把**构建机的用户目录**写死进 `application.yml`

- **文件**：`pom.xml:196-199`（`<filtering>true</filtering>`）+ `src/main/resources/application.yml:28`
- **证据**（打包产物里就是写死的绝对路径）：

```
target/classes/application.yml:28:    default-path: C:\\Users\\Leo/lion-code-workspace
src/main/resources/application.yml:28:    default-path: ${user.home}/lion-code-workspace
```

- **为什么是 bug**：`${user.home}` 被 maven 在**构建时**替换成构建机（`C:\Users\Leo`）的值，随 jar 分发出去。派生出来的路径全部指错：
  - `lion.event.store-path` → `C:\Users\Leo\lion-code-workspace\.lioncode\events`
  - `lion.plugin.scan-path` → 同上 `.lioncode\plugins`
  - 会话与对话历史目录（`SessionPersistence`/`ConversationHistory`）同样落在这个路径下（实测启动日志：`对话历史存储目录已初始化: C:\Users\Leo\lion-code-workspace\.lioncode\conversations`）
  在别人的机器上：普通用户**无权在 `C:\Users\` 下建目录**（需要管理员），于是事件/会话/历史持久化会静默失败（只留一行 error 日志），换机器就等于丢配置。同时它也让所有用 `-Duser.home=<临时目录>` 做隔离的自测套件**失去隔离**（实测本套件第一版就写进了真实用户目录，被沙箱拒绝才暴露出来）。
- **建议改法**（三选一）：
  1. `pom.xml` 的资源过滤排除 yml：`<nonFilteredFileExtensions>` 加 `yml`/`yaml`，或给 `<resource>` 加 `<excludes><exclude>application.yml</exclude></excludes>`；
  2. 或把 yml 里的 `${user.home}` 改成 Spring 的 SpEL：`#{systemProperties['user.home']}/lion-code-workspace`（运行时解析，且不会被 maven 过滤）；
  3. 或改成相对/中立默认（如 `${user.dir}/lion-code-workspace`），并在首次启动时按真实 home 生成配置。
  注意：改完要确认没有别的资源依赖过滤（yml 里没有 `@...@` 占位符，只有这一处 `${user.home}`）。
- **验证方式**：`python tools/checks/_check_audit_api_robustness.py` 的注释里记录了这个坑；改完后再跑一次，`target/classes/application.yml` 里应当仍是 `${user.home}`。

### D-2【中·待修】`mvn package` 在"有人正跑着应用"时会把 fat jar 覆盖成 thin jar

- **现象**：`spring-boot:repackage` 需要把 `target/lion-code-agent-harness-1.0.0-SNAPSHOT.jar` 改名为 `.jar.original` 再写新包；Windows 上正在被 JVM 打开（`java -jar`）的 jar 不允许改名，而 `maven-jar-plugin` 已经先写了一个**不含依赖的 thin jar**，于是失败后 target 里留下一个 0.78MB、**无法 `java -jar` 启动**的 jar。而所有 `tools/checks/_check_*.py` 套件都是 `java -jar target/...jar`。
- **影响**：审计期间我遇到两次（第一次别人的实例、第二次我自己的套件刚跑完）。表现为"套件突然全挂、报 NoClassDefFoundError"，排查成本高。
- **建议改法**：① 套件启动 app 时用 `java -cp target/classes:deps` 或从 `dist/` 里那份被复制的 jar 启动；② `_build.ps1` 在 package 前检测同名 jar 是否被占用并给出提示；③ 或让套件在 app 退出后再构建。
