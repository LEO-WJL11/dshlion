# 技能系统（通用 SKILL.md 格式）

## 一句话

技能不再是写死在 Java 里的四个类，而是**一个目录一份 `SKILL.md`**：
模型从系统提示词里的"技能目录"自己挑，用户也可以点名指定。

## 技能放在哪

| 来源 | 位置 | 优先级 |
| --- | --- | --- |
| 内置 | 仓库/安装目录下的 `skills/<id>/SKILL.md`（随包发布） | 低 |
| 用户 | `<用户主目录>/.lioncode/skills/<id>/SKILL.md` | 高（**同 id 覆盖内置**） |

`<用户主目录>/.lioncode/` 就是 `app-config.json` 所在的那个目录（跟着现有 `AppConfigStore` 走）。
目录名就是技能 id；`GET /api/skills` 会把两个目录的实际路径分别放在 `skillsDir` / `userSkillsDir` 里。

内置技能目录的查找顺序（和 `LocalModelRuntime.appDirs()` 一个思路，因为启动方式有好几种）：

1. `-Dlion.skills.dir=...`（显式指定）
2. `-Dlionbox.home=...` 下的 `skills/`
3. 进程工作目录下的 `skills/`、`dist/skills/`
4. jar 所在目录下的 `skills/`、`dist/skills/`，以及 jar 目录的上一级 `skills/`（开发时 jar 在 `target/`，技能在仓库根）

## SKILL.md 格式

```markdown
---
name: pdf                                  # 必填，唯一 id（= 目录名 = @skill:<id> 里的 id）
display_name: PDF 处理                      # 必填，界面上显示的名字
description: 一句话说明这个技能能干什么        # 必填，模型主要靠这句判断要不要用
when_to_use: 什么情况下该用                   # 必填，给模型看的触发条件
keywords: [pdf, 合并, 拆分]                 # 可选，关键词兜底匹配（命中就把正文直接注入）
tools: [read_file, execute_command]        # 可选，本技能要用到的工具名
mode: standard                             # 可选，minimal / standard / any（默认 any，目前只影响信息展示）
model: ""                                  # 可选，指定跑这个技能的模型（留空=当前模型）
version: 1.0.0                             # 可选
tags: [pdf, document]                      # 可选，分类标签
task_types: [合并PDF, 拆分PDF]              # 可选，任务类型描述
---

正文：给模型的具体指令（怎么写、注意什么、示例）。
```

必填字段缺任何一个，这个技能就会以"坏技能"的形态出现（见下）。

### 字段表（接口返回值对应关系）

| frontmatter | 列表接口字段 | 说明 |
| --- | --- | --- |
| `name` | `id` / `name` | 唯一 id（两个字段值相同，前端用哪个都行） |
| `display_name` | `displayName` | 显示名 |
| `description` | `description` | 一句话说明 |
| `when_to_use` | `whenToUse` | 触发条件 |
| `keywords` | `keywords` | 关键词兜底 |
| `tools` | `tools` | 需要的工具名 |
| `mode` | `mode` | minimal / standard / any |
| `model` | `model` | 指定模型（留空=当前模型） |
| `version` | `version` | 版本 |
| `tags` | `tags` | 标签 |
| `task_types` | `taskTypes` | 任务类型 |
| 正文 | `bodyPreview` / `bodyLines` | 正文预览与行数 |
| — | `enabled` / `builtin` / `source` / `error` | 是否启用 / 是否内置 / 文件路径 / 解析错误 |

## 模型怎么用上技能

1. **技能目录**：系统提示词里每个启用技能一行 —— `- backend — 后端开发技能：…（什么时候用：…）`，
   最多 20 行；并明确告诉模型："匹配当前任务时，先调 `skill_load`（参数 `name`）拿到完整指令，再动手"。
   目录里**不放正文**：正文全塞进去，每条消息都要多花上千 token 读一遍，本地模型 11 token/s，那就是一分钟。
2. **`skill_load` 工具**：`{"name": "backend"}` → 返回该技能正文。不存在 / 解析坏了 / 被禁用，三种情况分别给不同的、
   能照着改的提示（不要一律回"技能不存在"，模型会换个名字反复重试）。
3. **关键词兜底**：技能写了 `keywords`，且用户消息里出现这些词，正文会**直接注入**这一轮（老行为，保留）。
   四个内置技能由 `AgentLoop.buildSkillPrompt()` 走这条路；用户自己加的技能由 `SkillCatalogSpi` 补上。
   ASCII 关键词按词边界匹配（`api` 不会在 `rapid` 里命中、`java` 不会在 `javascript` 里命中），中文关键词按包含匹配。

## 用户指定技能（三种写法）

| 方式 | 写法 | 生效范围 |
| --- | --- | --- |
| 消息内点名 | `@skill:backend` 或 `/skill:backend` | 只这一轮（正文就地展开在该条消息里） |
| 会话钉住 | `POST /api/skills/active {sessionId, skills:[...]}` | 该会话之后每一轮（正文注入系统提示词） |
| 持久开关 | `POST /api/skills/{id}/enable` / `disable` | 全局，写进 `app-config.json` 的 `skills.disabled` |

被点名/被钉住的技能，正文**直接展开**，不需要模型再去调工具。

## 端点

统一响应外壳：顶层同时给 `ok`、`success`（项目老约定），数据既在顶层也在 `data` 里。

### `GET /api/skills`

```json
{
  "ok": true, "success": true, "message": "操作成功",
  "skillsDir": "C:\\...\\lion-code\\skills",
  "userSkillsDir": "C:\\Users\\leo\\.lioncode\\skills",
  "skills": [
    {
      "id": "backend", "name": "backend", "displayName": "后端开发技能",
      "description": "后端代码编写、调试、编译排错、接口设计、依赖处理等后端相关能力",
      "whenToUse": "用户要写/改/调试服务端代码…",
      "keywords": ["后端", "backend"], "tools": ["read_file", "execute_command"],
      "mode": "standard", "model": "",
      "enabled": true, "builtin": true,
      "source": "C:\\...\\skills\\backend\\SKILL.md",
      "error": null, "bodyPreview": "你具备专业的后端开发能力…",
      "version": "1.0.0", "tags": ["backend"], "taskTypes": ["后端代码编写"], "bodyLines": 42
    }
  ],
  "data": { "ok": true, "skillsDir": "...", "userSkillsDir": "...", "skills": [ ... ] }
}
```

### `POST /api/skills/{id}/enable` / `POST /api/skills/{id}/disable`

响应：`{ok, success, message, id, enabled}`。id 写 `backend` 或老的 `skill.backend` 都认。

### `POST /api/skills/reload`

重新扫描两个技能目录（用户改完文件不用重启）。
响应：`{ok, count, errorCount, skillsDir, userSkillsDir, skills:[...]}`。

### `GET /api/skills/active?sessionId=<id>` · `POST /api/skills/active`

`GET` → `{ok, sessionId, skills:["backend"]}`；
`POST` body `{sessionId, skills:["backend"]}` → `{ok, sessionId, skills:[...], unknown:[...]}`
（不认识的 id 会被忽略并列在 `unknown` 里；`skills: []` 表示取消钉住）。

## 坏技能：不影响启动

frontmatter 缺必填字段 / YAML 语法错 / 正文为空 / 文件编码是 GBK 的记事本文件（会按 UTF-8 → GBK 容错解码），
这些**都不会让应用起不来**：

- 技能照旧出现在 `GET /api/skills` 的列表里；
- `error` 字段写明原因（缺哪些字段、YAML 哪一行错），`enabled=false`；
- 它不参与提示词注入、`skill_load` 也加载不了（会回显上面那句错误）。

改好文件调一次 `POST /api/skills/reload` 即可。

## 四个内置技能

| id | 文件 | 能力 |
| --- | --- | --- |
| `backend` | `skills/backend/SKILL.md` | 后端代码编写、接口设计、编译排错、依赖与测试 |
| `client` | `skills/client/SKILL.md` | 桌面客户端（Electron/Qt/JavaFX/WPF）、打包分发 |
| `document` | `skills/document/SKILL.md` | 文档撰写、解析、格式转换、README/API 文档 |
| `frontend` | `skills/frontend/SKILL.md` | 网页前端、组件、样式调试、接口对接 |

原来的四个 Java 类（`BackendSkill` / `ClientSkill` / `DocumentSkill` / `FrontendSkill`）保留为**兼容壳**
（`FileBackedSkill` 的子类）：内容全部从 `SKILL.md` 读，`PluginRegistry`、`/api/plugins`、
`AgentLoop` 里的老路径都还认它们。加新技能**不需要**写 Java 类。

## 排错

| 现象 | 原因 / 处理 |
| --- | --- |
| 一个技能都没有 | `GET /api/skills` 看 `skillsDir` 是不是空的；从别的目录启动时用 `-Dlion.skills.dir=<仓库>/skills` |
| 用户技能不生效 | 确认路径是 `<user.home>/.lioncode/skills/<id>/SKILL.md`（两层，文件名必须叫 `SKILL.md`），然后 `POST /api/skills/reload` |
| 技能列出来了但模型不用 | 看 `description` / `when_to_use` 是否写清楚了 —— 模型就是靠这两句决定要不要 `skill_load` |
| 改了正文没生效 | 技能是启动时扫描+缓存的，改完调 `POST /api/skills/reload` |

## 已知限制

- 技能 id 只允许字母、数字、`.`、`_`、`-`（要能写进 `@skill:<id>`）；
- 技能扫描的层级固定是 `<技能目录>/<id>/SKILL.md`，不支持更深嵌套或别的文件名；
- `mode` 字段目前只作为信息展示（`minimal/standard/any`），没有按模式过滤技能；
- `model` 字段暂未接入模型路由（模型选择仍由会话/适配器决定）。
