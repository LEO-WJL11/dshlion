### 6. 修掉一个会误导用户的「自定义 API」默认值（含老配置迁移）

发现：`%USERPROFILE%\.lioncode\app-config.json` 里 `lionbox-custom`（「自定义 API」实例）
的 `baseUrl` 竟然是**本地端点** `http://127.0.0.1:8788/v1`。原因是
`AppConfigStore` 生成这个实例时传的是"当前生效的 baseUrl"，而默认模式是本地，于是就把本地端点抄了进去。

危害：自定义模式下本地运行时**不启动**，用户切过去如果没改地址，请求必然连接失败，
而且很难反应过来是自己没填。

修法（`AppConfigStore.java`）：
1. 新配置：自定义实例改用**存档**（`customApi`）里的端点与模型来初始化；
2. 老配置：新增一次性修复 `repairCustomProviderPointingAtLocal()` —— 只要发现自定义实例
   指向已知本地端点，就换成存档里的值；存档为空就留空，让界面空着提示用户填。

**迁移实测**（拿真实的老配置跑的，改动前先备份了配置）：

```
providerMode       : local                      ← 未变，当前模式没被动过
active baseUrl     : http://127.0.0.1:8788/v1   ← 未变
local  inst baseUrl: http://127.0.0.1:8788/v1   ← 未变
custom inst baseUrl: https://api.xiaomimimo.com/v1   ← 由本地端点修正为存档里的真实端点
custom inst models : mimo-v2.6-flash                 ← 同步补回存档里的模型
```

### 9. 预热与工具调用接线核对（读代码确认，未触发实际推理）

### 11. 测试踩到的两个坑（都记下来，避免下次误判）

1. **`Start-Process java` 拿到的是 `javapath` 垫片进程号**，杀掉它**不会**杀掉真正的 JVM。
   我第一次验证兜底时就是这样：残留实例还占着 8080，于是我查到的其实是**上一个实例**的
   `resolvedModelPath`（指向 repo 的 dist），差点得出"兜底没生效"的错误结论。
   正确做法：查 `Get-NetTCPConnection -LocalPort 8080` 的 **OwningProcess** 跟启动的 PID 对不对，
   或者直接用真 JVM 的全路径 `C:\Program Files\Java\jdk-26.0.2.1\bin\java.exe` 启动。
2. **验证任何"当前进程状态"之前先确认端口归属**。端口上是谁，你查到的就是谁——这句话在
   本机同时可能存在多个实例时尤其重要（e2e 测试、手动启动、安装后启动都可能撞在一起）。

### 23. 慢在哪：一次 380 秒的生成，和一份被服务端丢掉的 3102-token 工具定义

从本机 llama-server 日志里挖出来的事实（都是真跑的数据）：

## 2026-09-28 · 第 8 轮：工具调用"错了"的真因 —— 解析器不认 Qwen 模板原生格式

### 27. 现场

用户发「把所有工具都调用一遍我测试下」，界面/正文里看到的是：

```
🦁 我先了解工作区环境，然后逐个调用工具做测试。{"command": "ls -la && pwd"}
```

日志（`%TEMP%\lionbox-agent.log` 23:03:30）给出了原文和结论：

```
DEBUG ConversationHistory - 消息已添加到会话 …: [assistant] 我先了解工作区环境，然后逐个调用工具做测试。<tool_call><function=execute…
DEBUG AgentLoop - JSON工具调用解析失败: Unexpected character ('<' (code 60)): expected a valid value …
INFO  AgentLoop - === Agent主循环结束 === 共 0 轮工具调用
```

也就是：模型输出的是 **Qwen 模板原生格式**（llama-server 开 `--jinja` 时本来由服务端解析成
标准 tool_calls 的那种）：

```
<tool_call><function=execute_command><parameter=command>ls -la && pwd</parameter></function></tool_call>
```

而 harness 的解析器只认 `<name>/<arguments>` 和 JSON 两种，于是把这个文本拿去当 JSON 解析，
报 `Unexpected character ('<')` → **整轮工具调用作废，0 轮**。界面表现就是用户说的
"它说要调用工具，然后什么都没发生"。模型白生成一轮（还慢）。

### 28. 改法

新增 `QwenToolCallParser`（独立静态类，不依赖 Spring/Jackson，带 `main()` 自测）：

- 认 `<function=工具名>…</function>` + `<parameter=键>值</parameter>`，**有没有 `<tool_call>`
  外壳都认**；多调用、多参数、多行值（命令里的换行）都保留；
- 残缺块（没有 `</function>`）不硬凑、不崩；普通正文不会误判；
- `parseToolCallsFromText()` 把它排在**最前面**（模型最习惯的形式先试）；
- `removeToolCallBlocks()` 一并剥掉模板格式，正文里不再残留调用块；
- 提示词里把三种被接受的写法都写清楚（模型别在格式上纠结）。

顺带修一处**误导性日志**：原来打印的是 `toolDefinitions.size()`，文本模式下按设计就是 0，
于是日志写着「可用工具数量: 0」，看着像 54 个工具全丢了。现在分开报
「本轮可用工具 54 个（随请求下发 0 个；文本约定）」。

### 31. 三个根因

| 现象 | 根因 |
|---|---|
| 几乎每个工具"第一次失败、第二次成功" | 文本通道下不下发 tools 定义，提示词里只有「工具名 + 一句描述」，**参数名一个都没有**，模型只能猜；猜错一次 = 一整轮（本地 10~40 秒） |
| `create_directory` 同样参数连做 7 次 | harness 没有任何"这次调用是不是刚做过"的判断 |
| `fetch_url` 45 次 → 最终「处理超时」 | 网络工具 connect 15s + read 30s，对不可达的站点每次都耗满；45 轮把 ChatController 的 **10 分钟**上限吃光，用户只看到"处理超时"，不知道是某个工具在打转 |

### 32. 改法

1. **参数签名进提示词**：工具清单渲染成 `- modify_file(path*, operation*, ...)`，
   带 `*` 的是必填，并写一句「参数名必须照抄，写错或漏必填都会直接调用失败」。
   代价 258 token（提示词 1171 → 1429 token），换回来的是几十次往返。
2. **`ToolCallGuard`（新类，带自测）**：按会话统计「工具 + 参数指纹」与连续失败次数；
   同样的调用第 3 次起只提示不执行、第 5 次直接终止任务；同一工具连续失败 6 次后不再执行。
   每条用户消息开始时 `reset`（上一条消息里调过，这一条当然可以再调）。
3. **轮次上限 60**：跑飞时明确报「工具调用轮次过多」，而不是让前端 10 分钟超时来兜底。
4. **网络工具快速失败**：`UrlFetch/HttpGet/HttpPost/WebSearch` connect 15s→8s、read 30s→15s；
   `DownloadTool` connect 30s→10s（read 保留 120s，下载大文件要给足）。

`executeTool()` 也从 void 改成返回 boolean，把成功/失败回报给守卫
（识别"某个工具在连续失败还硬试"）。

### 35. 根因：中途塞 system 消息 = 模板直接抛异常

Qwen 的 Jinja 模板里有这么一条硬约束：

```
{{- raise_exception('System message must be at the beginning.') }}
```

而 harness 在跑的过程中会往历史里塞 system 消息（残缺调用纠正、单工具限制、
重复调用提醒），一旦触发纠错，下一次请求就被服务端 500 掉，整条消息报废。

### 36. 顺带纠正一个我说反了的前提

第 7 轮我写过「随包 llama-server 没开 --jinja，tools 会被服务端丢掉」，
并据此把本地模型强制切成文本通道。**这个前提是错的**，实测两下就露馅：

```
llama-server --help
  --jinja, --no-jinja   whether to use jinja template engine for chat (default: enabled)
```

```
# 直接打本机 8788，带 tools 发一次
finish_reason = length
结构化 tool_calls = {"type":"function","function":{"name":"list_directory","arguments":"{\"path\":…
```

即：Jinja 默认就是开的，模板会把 `tools` 渲染成提示词里的 `# Tools` 段
（还带 "Required parameters MUST be specified"），模型吐的 `<function=…>`
也被服务端解析成标准 tool_calls 回来了。**这才是这个模型训练时看到的样子。**

（同一份 `/props` 里 `chat_template_tool_use` 报 False，是误导项，别信它 ——
实测能渲染、能解析。教训：能力判断要打真接口，不要读标志位。）

### 37. 改法

1. **中途提示一律走 user 角色**：新增 `addNotice()`，内容带【系统提示】前缀；
   原来那些 `ConversationMessage.system(...)` 全部改掉（共 7 处）。
2. **buildMessages 加兜底**：历史里非首条的 system 消息，发出去前降级成 user。
   老会话文件里已经存了这种消息，不兜底那个会话会永远 500。
3. **本地模型回到原生 function calling**（`useNativeTools()` 去掉"本地→文本"那条规则）。
   好处：参数名/必填项由模板保证，1.1.4 里"工具第一次调用老失败"那类问题从源头消失。
   文本 `<tool_call>` 解析器（QwenToolCallParser）继续当兜底。
4. **原生通道下不再手写工具清单**：模板已经渲染了 `# Tools`，我们那份是重复的。
   提示词因此从 1240 token 降到 **471 token**（标准模式，实测 /tokenize）。
