### 107. 网络搜索：从占位实现到无头浏览器

原来那个 `web_search` 根本不能用（只回一句“需要配置搜索 API 密钥”）。
现在用系统里**已经装好的 Edge/Chrome** 打开结果页，把渲染后的 DOM 抓回来自己解析：

- `HeadlessBrowser`：用 `--headless=new --dump-dom`，**一次调用一个进程**，
  不用 CDP/WebSocket、不占端口、不留常驻进程；找不到浏览器时会如实说明原因；
- 搜索默认走 cn.bing.com（国内能直连），也可以指定 duckduckgo / google / baidu；
  一个引擎一条没解析到就换另一个再试；
- 浏览器不可用/拿不到内容时，退到 HTTP 直取同一个结果页（Bing 是服务端渲染的），
  结果里写明“方式：无头浏览器 msedge.exe”或“HTTP 直取（原因）”，不偷偷换路。

两个真坑（都是实测出来的）：
1. **只读 stdout 不读 stderr 会死锁**：Edge 一启动就往 stderr 写 5KB+ 日志，
   管道写满后浏览器就卡着不退出 —— 表现就是“超时 30 秒被收掉、没吐出内容”。
   现在 stdout/stderr 各开一个线程抽干（stderr 只留一小段做诊断）；
2. PowerShell 里 `& $edge ...` 直接抓输出是空的（浏览器不跟控制台玩），
   得重定向到文件才看得到 DOM —— 晴天验证时差点以为浏览器不能用。

### 108. 修好的工具（用户实测报告的那几个）

### 115. 报错工具的真因：参数是字符串，工具却硬转 Number

极简模式那一跑的 ❌（head_tail_file / line_count / word_count /
modify_file）**不是工具逻辑错**，而是本地盒子默认走的
**文本通道下所有参数都是字符串**，而工具里写的是
`((Number) arguments.get("lines")).intValue()`：

```
java.lang.ClassCastException: class java.lang.String cannot be cast to class java.lang.Number
```

一个数字参数就能废掉一个工具。底层统一收口：`AbstractToolPlugin` 新增
`getIntArg()` / `getBoolArg()`，字符串、数字、布尔、`"5 行"`、`"true"`、`"是"` 全认，
认不出来就用默认值（不抛异常）。**14 处 Number 强转 + 8 处布尔强转全部换掉**
（head_tail_file、read_file、list_directory、glob_files、search_in_files、directory_tree、
modify_file、git_log、uuid、fetch_url、execute_command、change_permissions…）。

另外四个真实缺陷：

| 工具 | 原来 | 现在 |
|---|---|---|
| `line_count` | `Files.lines()` 严格 UTF-8 解码，GBK 文件报 `MalformedInputException` | 跟 word_count 一样容错读（UTF-8 → GBK） |
| `modify_file` | 文件不存在就只回一句"文件不存在" | `operation=create` 直接新建（已存在则整体覆盖） |

### 116. 模式与工具集：标准 55 个，极简 21 个

`WebSearchTool` 里一直写着 `isAvailableInMode() { return true; }`（搜索工具的"永远可用"老特例），
所以极简模式（只该有文件类 + shell 类）里还能调 web_search。现在：

- 删掉那个特例，交给基类按"模式 + 类别"统一判断；
- 极简模式的允许列表加上 `FILE_SEARCH`（glob_files / search_in_files 也是文件工具）；
- 极简模式的**系统提示词里直接列出真实可用的工具名**（模型对"文件工具"的
  理解是它训练里那套名字，不列它就去试 list_files 这种不存在的名字）。

实测：标准模式 **55 个**工具；极简模式 **21 个**（文件类 18 + shell 类 3），
不含 web_search / timestamp / git_* / hash ……

### 117. execute_command = 一个持续运行的终端

原来是"一条命令起一个进程"（`powershell -Command "..."` 跑完就退），
所以 `cd` 是白做的、`$env:X=1` 下一轮就没。现在新增
`PersistentShell`：**同一个工作区共用一个长期活着的 PowerShell 会话**。

协议里解决的三个坑（都是实测踩出来的）：

1. **多行脚本**：PowerShell 5.1 的 `-Command -` 是**按行**读 stdin 的，直接喂
   `if (...) {` 换行 `}` 会被拆散卡住 → 命令先做 UTF-8 Base64，
   整条作为**一行 ASCII** 送进去，里面 `Invoke-Expression` 当一整段脚本执行；
2. **中文乱码**：PS 5.1 的 stdin/stdout 走系统代码页（中文机器 = GBK），
   UTF-8 写命令进去进去之前就乱了 → Base64 全程 ASCII 从根上绕过，
   出来的那边会话建立时设一次 `[Console]::OutputEncoding = UTF8`；
3. **哪段输出属于哪条命令**：每条命令跑完由 shell 自己打一行唯一哨兵
   `__LIONBOX_DONE_<随机>__ ok=... code=... cwd=...`，读到哨兵就收工。

超时不再只杀子进程（那样会话本身也废了）：**连整个会话一起杀掉重建**，
并在结果里明说"终端已重启，之前 cd 的目录和变量没了"。

### 118. 界面工具行重复刷屏的真因

事件时间戳带纳秒，而界面轮询只能给毫秒（`?after=<ms>`）。后端原来是
`timestamp.isAfter(Instant.ofEpochMilli(after))` —— "纳秒的 .123456789 比毫秒的 .123 大"
**永远成立**，于是每轮轮询（800ms 一次）都把同一条 `TOOL_CALL_START` 重新返回，
界面就再画一遍 —— 重复次数正好 = 那条工具跑了几秒 ÷ 0.8s（web_search 7 秒 = 9 行）。

现在：后端按毫秒 + **含边界**比较（不丢事件），界面按 `eventId` 去重（不重复画）。
