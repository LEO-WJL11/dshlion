## 2026-09-29 · 第 31 轮：编译和打包都用 16 线程 + 全量清缓存重编

用户两条要求：**“编译和打包都用16线程”**、
**“Java 26 代码改完后要重新编译整个项目（清空所有编译缓存）”**。

- 编译：`mvn -o -T 16 -DskipTests clean package`（`-T 16` 并行，`-o` 离线，
  **默认带 clean**）；清掉整个 target 后 202 个 class 全量重生成，实测 **~5 秒**。
- 打包：`LZMANumBlockThreads=16`。实测发现 **solid 压缩是单流的**，开着
  `SolidCompression=yes` 时多线程设置等于没用：
  ultra64+solid+16 线程 = 31.0 秒 / 72.19 MB；ultra64+关solid+16 线程 = **23.6 秒 / 73.96 MB**；
  lzma2/max+关solid+16 线程 = 22.2 秒 / 74.07 MB。取中间：保住 ultra64，多 1.8 MB 换 7.4 秒。
- 新增 `_build.ps1`：清 target 全量重编 → 复制 jar 到 dist → ISCC 出包，打印两步耗时与包的 sha256。

### 100. 顺带查出并修掉两件事

**① 测试假失败：运行时端口撞上用户自己的 llama-server。**
`_check_model_choice.py` 里那个测试 app 用默认运行时端口 8788，而**用户自己那台
LionBox 的 llama-server 正跑在 8788**。于是 `healthy()` 一探测就返回 true，`ensureRunning()`
直接返回，永远走不到“下载配置的那份”分支 —— 第二阶段全线失败。
不是功能 bug，是测试隔离没做干净：现在测试显式 `--lionbox.runtime.port=8790`。

**② 日志刷屏：兜底警告每次状态查询都打。**
进度条每 1.5 秒查一次 `/api/runtime/local`，`status()` 每次都调 `resolvesModel()`，
那条“配置的模型 X 不可用”就跟着刷（一轮测试几百行）。
现在同一对（配置的 / 实际用的）**只打一次**。
