# LionBox / Lion-Code Agent Harness —— 三种发布形态调研

- 调研日期：**2026-09-30**（所有版本号均以当日官方文档 / 官方仓库 / npm registry 的实际返回为准，不凭记忆）
- 调研对象：把已有的单文件 Web UI（`web/index.html`，后端 Spring Boot 跑在 `http://127.0.0.1:8080`，REST 前缀 `/api`）以三种形态发布
- 已核实的本机环境：Node.js `v26.7.0`、npm `11.19.0`、`java` 为 JDK `26.0.2.1`、真 Maven 在 `C:\Users\Leo\.maven\apache-maven-3.9.10\bin\mvn.cmd`、后端当前**已在** `127.0.0.1:8080` 上运行（`GET /api/runtime/mode` 返回 HTTP 200）

> 结论先行：三种形态都**不重写界面**，统一用「加载现有 8080 页面」的方式复用 WebUI。Electron 复用度最高（整窗就是 WebUI），VS Code 与 JetBrains 用内嵌浏览器（iframe / JCEF）承载同一页面。真正的分水岭不是"能不能显示"，而是**分发链路**：Electron 要解决代码签名 + 自动更新，JetBrains 要解决 `since-build/until-build` + 签名，VS Code 要解决 Marketplace 的 PAT 退役（2026-12-01）。

## 2. 三种形态对比表

| 维度 | ① Electron 套壳 | ② JetBrains IDE 插件 | ③ VS Code 扩展 |
| --- | --- | --- | --- |
| 复用现有 WebUI 的方式 | 主进程 `BrowserWindow.loadURL('http://127.0.0.1:8080')`，整窗即 WebUI，**零改动** | Tool Window + `JBCefBrowser.loadURL(...)`（JCEF 内嵌 Chromium） | `WebviewPanel` + 自建 HTML 里的 `<iframe src="http://127.0.0.1:8080/">`（不能直接 `webview.html = 页面源码`，否则相对路径 `/api/*` 会指向 webview 源而失效） |
| 最小可用关键 API | `app.whenReady()`、`new BrowserWindow({webPreferences})`、`win.loadURL()`、`contextBridge.exposeInMainWorld()`、`session.setPermissionRequestHandler()`、`webContents.setWindowOpenHandler()` | `ToolWindowFactory.createToolWindowContent()`、`ContentFactory.getInstance().createContent()`、`JBCefApp.isSupported()`、`new JBCefBrowser()`、`browser.getComponent()`、`browser.loadURL()`、`Disposer.dispose()` | `window.createWebviewPanel()`、`WebviewPanel.webview.html`、`webview.options.enableScripts`、`webview.asWebviewUri`（本例不需要）、`webview.onDidReceiveMessage`、`commands.registerCommand` |
| 安全设置要点 | `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、`webSecurity: true`、不开 `allowRunningInsecureContent`；远程内容只经 preload 白名单 IPC | JCEF 默认隔离；不要在页面里暴露插件 API（用 `JBCefJSQuery` 显式桥接，非必要不桥接） | Webview 必须自带 CSP；把 `frame-src http://127.0.0.1:8080` 加白，脚本用 nonce |
| 开发量（在现有 WebUI 之上） | 小：1 个主进程 + 1 个 preload + 1 个等待页，约 200 行 JS；主要工在打包/签名 | 中：Gradle 工程 + plugin.xml + 1 个 `ToolWindowFactory` + 1 个 Swing 面板（含健康检查与重试），约 200 行 Java | 最小：1 个 `extension.js`（约 150 行）+ package.json contributes |
| 打包/分发 | `electron-builder` 出 `.exe`/NSIS/MSI/dmg/AppImage；或 Electron Forge `make` | `./gradlew buildPlugin` 出 `build/distributions/*.zip` → 手动上传 marketplace（**首次必须手动上传**），之后 `publishPlugin` | `vsce package` 出 `.vsix`；`vsce publish` 上传 Marketplace |
| 本地安装方式 | 直接跑安装包；开发期 `npm start` | `Settings → Plugins → ⚙ → Install Plugin from Disk...` 选 zip | `code --install-extension lionbox-0.0.1.vsix` 或 Extensions 视图 "Install from VSIX..." |
| 签名要求 | **强制建议**：Windows 需代码签名证书（否则 SmartScreen 拦截），macOS 需 Developer ID 签名 + 公证；官方明确"code signing 是自动更新的前置条件" | Marketplace **必须签名**：`signPlugin` 先于 `publishPlugin` 自动执行，需自备证书链（`CERTIFICATE_CHAIN`/`PRIVATE_KEY`/`PRIVATE_KEY_PASSWORD`） | 不需要代码签名；但发布身份走 Azure DevOps/Microsoft 账号，**PAT 于 2026-12-01 全局退役**，官方要求改用 Entra ID + workload identity federation |
| 自动更新 | 需要自建更新源：`autoUpdater` + electron-builder 的 `latest.yml`/更新服务器，或更新包全量分发 | Marketplace 托管：用户 IDE 自动提示更新（非默认频道需用户自加仓库 URL，如 `/plugins/beta/list`） | Marketplace 托管：自动更新；也可 `vsce publish --pre-release` 走预发布通道（`engines.vscode >= 1.63.0`） |
| 主要风险点 | ① 首次运行需等后端起来 → 必须做健康轮询，不能直接 `loadURL`；② 随包带 jar 会显著增大体积且 Java 运行时不在包内（目标机需自带 JRE 或另打包 jlink）；③ 端口 8080 冲突/被占用；④ 未签名即被 SmartScreen/macOS Gatekeeper 拦；⑤ 加载 `http://127.0.0.1` 属"非安全协议"，但 `127.0.0.1` 是 Chromium 的 potentially-trustworthy origin，实际不触发混合内容拦截 | ① `since-build/until-build` 写错会被 Plugin Verifier 拒（官方明说"编造的 build number 会被拒"）；② **JCEF 依赖变更**：2026.2 起必须显式声明 `<depends>com.intellij.modules.jcef</depends>`（该别名自 2025.3.1 起可用，更早版本没有 → 想要更宽兼容区间只能拆分支发版）；③ `until-build` 不写=兼容所有未来版本（官方推荐做法），写死则每次大版本都要重发；④ JCEF 在某些自定义 JBR 下不可用，必须 `JBCefApp.isSupported()` 兜底；⑤ `useInstaller = false` 的构建已知 JCEF 不加载 | ① Webview 的 CSP 必须自行声明，否则 iframe 被拦；② Webview 内存开销大，官方明确建议"能不用就不用"；③ `retainContextWhenHidden` 保状态但吃内存；④ 远程开发（Remote-SSH/Codespaces）场景下 webview 在用户侧、扩展在远端，`127.0.0.1:8080` 指向的是**用户本机**而非扩展宿主 → 需要提示用户在远程机上跑后端；⑤ Marketplace 发布链路正在从 PAT 迁到 Entra ID |
| 适合的发布节奏 | 面向普通用户，一个安装包解决一切 | 面向已有 JetBrains 用户，IDE 内一键装 | 面向已有 VS Code 用户，IDE 内一键装（最轻） |

### 关键官方结论 + 链接（逐条可核查）

**Electron**
- 主进程 / 渲染进程模型与 preload：远程内容**绝不能**开 Node 集成，必须 `nodeIntegration: false` + `contextIsolation: true`，需要 Node 能力时用 preload + `contextBridge` 暴露白名单 API —— <https://www.electronjs.org/docs/latest/tutorial/security>（"Do not enable Node.js integration for remote content" / "Enable Context Isolation"）
- `BrowserWindow` 与 `loadURL`：<https://www.electronjs.org/docs/latest/api/browser-window>
- 打包：Electron 核心**不带**打包工具，官方推荐 Electron Forge（`npm run make`，内部组合 `@electron/packager` 等）；也可手动打包 —— <https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging>

**JetBrains / IntelliJ Platform**

### 混合内容 / 端口说明（三形态共通）
`http://127.0.0.1:8080` 与 `http://localhost:8080` 在 Chromium 里属于 *potentially trustworthy origin*，因此 VS Code Webview（自定义 scheme 源）与 Electron（`file://` 或自定义源）里内嵌这个地址**不会被混合内容策略拦截**；但 Webview 的 CSP 仍必须显式放行 `frame-src http://127.0.0.1:8080`。JetBrains JCEF 不受 Webview CSP 约束，但 IDE 处在代理/离线环境下时 JCEF 可能拿不到 `127.0.0.1` 之外的东西——我们只访问本机，无此问题。

### 后端就绪检测（三形态共通，统一用同一探针）
`GET http://127.0.0.1:8080/api/runtime/mode` —— **只要收到任何 HTTP 响应（含 404/401）就说明端口已监听**，只有连接被拒/超时才判定"未就绪"。三个工程都实现了同一策略（Electron 主进程 `http.get`、VS Code `fetch` + `AbortController`、JetBrains `java.net.http.HttpClient`）。
